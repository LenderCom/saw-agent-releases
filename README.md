# saw-agent releases

Signed release artifacts for the SAW remote agent.

- Channels: `dev` (prereleases, tag `dev-v*`) and `stable` (tag `v*`).
- Each release carries `manifest.json` + `manifest.json.minisig` (minisign-signed: version, channel, commit, min_version, artifact sha256s).
- **Yank** = re-publish the manifest with `yanked: true`. **Never delete releases** — a deleted head would downgrade the fleet.
- Publishing is CI-only (saw-agent release lanes). Token custody: see saw-docs plan/saw-agent-auto-update-plan.md §2.7.
- `scripts/staleness-check.sh` is the fleet-staleness alarm (see `.github/workflows/staleness-cron.yml`, every 6h). It talks to the fleet endpoint's real Envelope response shape (`{ok, data: {channels, machines}}`) and, if the check itself fails (bad HTTP status, malformed body), posts a distinct "staleness-check itself failed" Discord notice before exiting non-zero — the alarm mechanism failing is never silent. `./scripts/staleness-check.self-test.sh` drives it against a local mock of GitHub/fleet/Discord with real envelope-shaped fixtures and asserts the healthy/alarm/failure-notice outcomes; run it after touching the script.
- `scripts/fleet-health-check.sh` is a sibling alarm over the SAME fleet endpoint (see `.github/workflows/fleet-health-cron.yml`, every 1h — tighter than the staleness cron because the signals below are urgent) covering three per-machine signals the staleness check doesn't: (1) **security** — a machine's `updateError` indicates a genuinely tampered/corrupt manifest (`bad-signature` / a signature mismatch — the signer's key IS trusted but the bytes don't verify, per the plan §2.3.6, saw-agent `internal/update/verify.go` `VerdictBadSignature`, agents-api `IManifestVerifier.cs` `BadSignature`) → a distinct, high-priority `⚠️ SECURITY: agent <id> reported <error> for <target>` Discord message; (2) **ops** — a machine's `updateError` is `untrusted-key` (a well-formed signature from a key ID outside our embedded set — a stale key set, e.g. a machine lagging a key rotation; the SAME sources classify this as an ops event, NOT a security incident) → a SEPARATE, lower-priority `ℹ️ ops: agent <id> reported untrusted-key for <target> — likely a key-rotation lag; ensure it updates` Discord message, so a rotation window doesn't page every lagging machine as a security incident and bury a real compromise; (3) **stuck** — a machine sitting in a non-terminal update phase (`staged`/`draining`/`swapping`/`confirming`) with `lastUpdateAt` older than 30 minutes → a "stuck" alert naming the machine, phase, and age. Reuses the same envelope-unwrap, `ok` assertion, ERR-trap self-failure notice, and Discord bot secrets as `staleness-check.sh`. Dedup is a best-effort `STATE_FILE` cache keyed by machineId (per condition: security / ops / stuck) — the same machine + condition re-alerts only after a cooldown (default 6h each); **this is a per-run GitHub Actions cache, not a durable store — a cache miss (a bad restore, cache eviction) makes the check degrade to paging every run for a persisting condition, which is the accepted fallback (a repeated alert beats a silently swallowed one).** `./scripts/fleet-health-check.self-test.sh` covers bad-signature→security-alarm, untrusted-key→ops-alarm-not-security, stuck-draining→stuck-alarm, all-healthy→silent, an in-flight update under threshold→silent, dedup-suppresses-a-repeat, and the failure-notice path.
