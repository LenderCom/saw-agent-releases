# saw-agent releases

Signed release artifacts for the SAW remote agent.

- Channels: `dev` (prereleases, tag `dev-v*`) and `stable` (tag `v*`).
- Each release carries `manifest.json` + `manifest.json.minisig` (minisign-signed: version, channel, commit, min_version, artifact sha256s).
- **Yank** = re-publish the manifest with `yanked: true`. **Never delete releases** — a deleted head would downgrade the fleet.
- Publishing is CI-only (saw-agent release lanes). Token custody: see saw-docs plan/saw-agent-auto-update-plan.md §2.7.
- `scripts/staleness-check.sh` is the fleet-staleness alarm (see `.github/workflows/staleness-cron.yml`, every 6h). It talks to the fleet endpoint's real Envelope response shape (`{ok, data: {channels, machines}}`) and, if the check itself fails (bad HTTP status, malformed body), posts a distinct "staleness-check itself failed" Discord notice before exiting non-zero — the alarm mechanism failing is never silent. `./scripts/staleness-check.self-test.sh` drives it against a local mock of GitHub/fleet/Discord with real envelope-shaped fixtures and asserts the healthy/alarm/failure-notice outcomes; run it after touching the script.
- `scripts/fleet-health-check.sh` is a sibling alarm over the SAME fleet endpoint (see `.github/workflows/fleet-health-cron.yml`, every 1h — tighter than the staleness cron because both signals below are urgent) covering two per-machine signals the staleness check doesn't: (1) **security** — a machine's `updateError` indicates a signature-verify failure (`bad-signature` / `untrusted-key` / a signature mismatch) → a distinct, high-priority `⚠️ SECURITY: agent <id> reported <error> for <target>` Discord message; (2) **stuck** — a machine sitting in a non-terminal update phase (`staged`/`draining`/`swapping`/`confirming`) with `lastUpdateAt` older than 30 minutes → a "stuck" alert naming the machine, phase, and age. Reuses the same envelope-unwrap, `ok` assertion, ERR-trap self-failure notice, and Discord bot secrets as `staleness-check.sh`. Dedup is a best-effort `STATE_FILE` cache keyed by machineId — the same machine + condition re-alerts only after a cooldown (default 6h); **this is a per-run GitHub Actions cache, not a durable store — a cache miss (a bad restore, cache eviction) makes the check degrade to paging every run for a persisting condition, which is the accepted fallback (a repeated alert beats a silently swallowed one).** `./scripts/fleet-health-check.self-test.sh` covers bad-signature→security-alarm, stuck-draining→stuck-alarm, all-healthy→silent, an in-flight update under threshold→silent, dedup-suppresses-a-repeat, and the failure-notice path.
